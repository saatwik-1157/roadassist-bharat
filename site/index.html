India has 63 lakh kilometres of road. Most of it sits outside any organised assistance network, and a good share of it has no signal. RoadAssist reaches every vehicle, every phone and every road — including the ones with no bars.

This is not a mockup. The platform runs: 52 database tables, a live API, a booking state machine, geospatial dispatch, and a complete journey that works from a ₹1,200 feature phone over SMS.

    Proven by test

    Illegal transitions are impossible

    Sending work.complete to a booking that is still matching returns 409 and lists the commands that are legal there. The state machine is the authority, not the client.

    Proven by test

    A stolen session dies instantly

    Refresh tokens rotate on every use. Replaying a consumed one is treated as theft: the entire token family is revoked, including the token that had legitimately replaced it.

    Proven by test

    Nobody reads anyone else's data

    A second account gets 403 reading the booking, and 403 trying to book against a vehicle it does not own. Authorisation is checked at the resource, not just the route.

    Proven by test

    Replaying a request cannot double-book

    Every write accepts an idempotency key. Sending the same booking twice on a flaky connection returns the original reference instead of creating a second job — because on 2G, retries are normal.

    Proven by test

    The AI can be switched off

    Diagnosis runs on a deterministic rules engine behind the same contract a model will use. There is nothing to fall back from — the fallback is what ships, and every response says which one answered.

    Proven by test

    Queued work replays exactly once

    Actions taken offline carry a client-generated operation id. Submitting the same batch twice returns applied then duplicate.

    [ THE JOURNEY ]

    From breakdown
    to back on the road.

    Marked in kilometres, because that is how RoadAssist actually locates you when there is no street address — by the nearest highway marker.

    KM 00BREAKDOWN

    Something goes wrong

    A vehicle stops, or the on-device model detects a crash. Neither needs a network — detection runs on the handset.

    KM 00DIAGNOSE

    The phone works out what's wrong

    Describe it, photograph it, or plug in an OBD reader. The rules engine returns the likely fault, a severity, the parts needed and a drivability verdict — offline, in milliseconds.

    KM 04DISPATCH

    The nearest verified mechanic is found

    A PostGIS query ranks mechanics by distance, rating, availability and a small exploration bonus that keeps work from concentrating on a handful of names.

    KM 12TRACK

    You watch them arrive

    Live location, sampled less often while the mechanic is stationary so it costs roughly 4% battery an hour.

    KM 12RESOLVE

    Fixed, invoiced, paid

    Itemised invoice with GST, cashless or cash, and a rating that feeds back into how dispatch ranks that mechanic next time.

    [ THE DIFFERENCE ]

    Offline is the
    normal case.

    An assistance app that needs the internet fails at exactly the moment it is needed. So the network is treated as absent by default and its presence as a bonus. Flip the switch in the panel at the top to see it.

    On-device intelligence

    Diagnosis and crash detection run on the handset — no round trip, no dependency on a tower being in range.

    ≤ 15 MB · 120 ms

    Local write queue

    The request is stored on the device and marked pending. SOS always jumps ahead of everything else in the queue.

    Priority ordered

    Deferred sync

    On reconnect the queue replays. Conflict rules were written before any sync code, and booking state is always decided by the server.

    Server authoritative

    SMS fallback

    When there is no data at all, the whole core journey still completes over text — and the SOS path shares no runtime dependency with the platform.

    [ CLOUD ARCHITECTURE ]

    We consume two layers
    and provide a third.

    Demand swings roughly ten times between the quietest and busiest hour of a day, and spikes again through monsoon. Owned hardware would be sized for the peak and idle for twenty hours. Cloud is the enabling condition, not the hosting choice.

    Software as a Service

    What our users actually touch

    Seven client types share one multi-tenant deployment. Citizens, mechanics, fleet operators and government officers are isolated by row-level security and a separate encryption key per tenant — which is why one deployment can serve four audiences without their data ever meeting.

    Android / iOS appWeb PWAMechanic app Fleet dashboardGovernment portalAdmin console SMS · IVR · USSD

    Platform as a Service

    What we build on and never patch

    Managed services carry the operational work a four-person team cannot: failover, patching, backups. Provider portability is kept through containers and infrastructure as code, so lock-in stays a migration rather than a rewrite.

    Managed KubernetesManaged PostgreSQL + PostGIS Managed RedisManaged event busObject storage Metrics · logs · traces

    Infrastructure as a Service

    What runs it all

    Virtual servers built from hardened images inside a private network with exactly one internet-facing gateway. Nodes are replaced, never patched in place — affordable only because the services on them are stateless. Every byte stays in Indian regions.

    [ ARCHITECTURE DECISIONS ]

    Six decisions
    worth defending.

    Recorded before implementation. Each names the options considered and what the choice costs us — a decision without a stated cost is a preference.

    The architecture shows twelve services. A four-person team has to operate whatever it builds, and every independently deployed service adds a pipeline, a dashboard, an alert route and a failure mode.

    So: one deployable with enforced modules, each owning its own schema — plus one exception, the emergency service.

    What it costs: we have to say plainly that this is one deployable, not twelve running services. Claiming otherwise fails the first follow-up question.

    Every team that kept a monolith modular by asking people nicely has failed, usually in the last fortnight before a deadline.

    A build gate checks the dependency graph on every pull request: _shared ← identity ← fleet ← service ← ops. Adding an edge is a deliberate act that shows up in the diff.

    What it costs: a legitimate new dependency needs a config change and a reviewer's attention. That friction is the point.

    The domain is transactional — bookings, invoices and state transitions need real constraints — and heavily geospatial. PostGIS turns "nearest available mechanic" into an indexed query that measures 19.8 ms on real data.

    What it costs: telemetry at national scale will eventually need partitioning. The column layout is already designed for that migration.

    Two devices can edit the same booking while both are disconnected. Discover the rules while implementing and you encode whichever behaviour was easiest.

    So every field's rule was fixed first. Booking status: server wins, always. Odometer: max wins, because odometers only increase. Emergency contacts: the user decides — too important to guess.

    What it costs: more design before the first line of sync code, and a conflict log we have to actually read.

    Every other feature can fail for ten minutes and cost money. This one carries the opposite risk too: a false positive sending a real ambulance to a speed breaker.

    Isolation — its own deployable, quota and zones, with a degraded path sharing no runtime dependency. Confirmation — the model writes a signal; escalation requires recorded human confirmation, enforced in code by a column that must be non-null before any handoff.

    What it costs: emergency is exempt from spot instances and aggressive downscaling. It costs more, deliberately.

    We have no proprietary training data at project start. Wait for models and the product does not exist for two reviews; depend on models and a bad model becomes an outage.

    So every capability is an endpoint with a fixed contract, implemented with deterministic rules first. A model may only ever make a drivability verdict stricter — never declare safe what the rules called unsafe.

    What it costs: the rules are not scaffolding — they are the permanent production fallback and carry the same test coverage as the models.

    [ RUN IT YOURSELF ]

    Four commands
    to a working system.

    Needs Docker and Node 20+. No cloud account, no API keys — every external provider falls back to a local implementation, which is exactly how the offline story is testable.

    git clone <repo> && cd app
npm install
npm run infra:up          # PostgreSQL + PostGIS + Redis
npm run db:migrate && npm run db:seed
npm start                 # → http://localhost:4000
    Verify

    npm run verify

    Typecheck, lint, the module-boundary fitness function, and 9 schema tests that enforce the ADRs — including one asserting that raw model input is never stored, only a hash.

    Prove

    npm run test:e2e

    60 assertions driving the live API through the whole journey: auth, theft detection, diagnosis, dispatch, the state machine, invoicing, offline replay, tenant isolation, the emergency path and the SMS channel.
